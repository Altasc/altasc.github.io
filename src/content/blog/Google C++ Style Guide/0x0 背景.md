C++ 是 Google 众多开源项目所使用的主要开发语言之一。正如每一位 C++ 程序员所知的那样，这门语言拥有许多极其强大的特性，但往往这种强大也伴随着复杂性，进而导致代码更容易产生 Bug，也更难于阅读和维护。

本指南旨在通过详细阐述编写 C++ 代码时的“准则与禁忌”（Dos and Don'ts）来管控这种复杂性。这些规则的存在是为了保证代码库易于维护的同时依然能让开发者高效地使用 C++ 的语言特性。

“*代码风格*”，也被称为“可读性”，是我们用来指代规范 C++ 代码的一系列约定的总称。不过称之为“风格”多少有些名不副实，因为这些约定所涵盖的范围远不止如何格式化代码源文件那么简单。

Google 开发的大多数开源项目都遵循本指南中的要求。

请注意，本指南并非 C++ 教程：我们假定读者已经掌握了这门语言。

## 指南的目标

为什么我们会有这样的一个文档？

我们认为本指南应服务于几个核心目标。这些目标构成了所有具体规则背后的底层逻辑。通过明确阐述这些理念，我们希望为相关的讨论有据可依，并向更加广泛的社区阐明为什么制定这些规则以及为什么做出了某些特定决策。只要大家理解了每条规则所服务的具体目标，就能更加清楚某条规则在哪些情况下可以破例豁免（部分规则确实可以免除），以及若要修改指南中的某条规则，需要提出怎样的论据或替代方案。

就我们目前所见，本风格指南的核心目标如下：

### 风格规则必须物有所值 <br> Style rules should pull their weight

一条风格规则的收益必须足够显著，才值得要求我们所有的工程师去记住它。这种收益是相对于“在没有这条规则的情况下，代码库会变成什么样”来衡量的。因此，如果大家本来就不太可能去采用某种非常有害的编码方式编写代码，那么即使专门制定规则去禁止它，收益也是微乎其微的。这个原则主要解释了为什么我们没有制定某些规则，而不是解释为什么我们制定了哪些规则。例如，`goto` 违反了后文提到的诸多原则，但由于它本生已经极少出现，所以指南就没有对其做专门探讨。

### 为读者优化，而非为作者优化 <br> Optimize for the reader, not the writer

我们的代码库（以及提交给其中的大多数独立组件）预计会持续存在相当长的一段时间。因此，花费在阅读大多数代码上的时间，将远多于编写它们的时间。我们明确针对普通软件工程师优化在我们的代码库中阅读、维护和调试代码的体验，而不是针对作者优化编写这些代码时的便利。“给读者留下线索（痕迹）”是该原则下一个尤为典型的衍生细则：当一段代码中发生反直觉或非同寻常的行为时（例如，指针所有权的转移），在调用处为读者留下文本提示是极具价值的（`std::unique_ptr` 在调用处明确地展示了所有权转移）。

### 与现有代码保持一致 <br> Be consistent with existing code

在整个代码库中自始至终地保持同一风格可以让我们专注于其他（更重要的）问题。风格的一致性也让自动化成为可能：代码格式化工具或头文件整理工具只有在代码符合工具预期的前提下才能正常运作。在许多情况下，归入“保持一致”范畴的规则，本质上都可以归结为“挑一种定下来就别再纠结了”。一旦在这些细枝末节上允许灵活，人们为此争论所付出的代价将会远大于其潜在价值。然而，一致性也有边界的；在既缺乏明确的技术优劣论据、又没有长远演进方向时，它是一个很好的打破僵局的决定性因素（tie breaker）。一致性在局部范围内（例如单个文件内，或一组高度相关的接口之间）的约束力更强。在通常情况下，一致性不应被当作坚持旧的代码风格而不考虑新的代码风格的优点或者无视代码库随时间推移必然逐步向新风格收敛演进的趋势的挡箭牌。

### 适当时与广大的 C++ 社区保持一致 <br> Be consistent with the broader C++ community when appropriate

与其他组织或业界使用 C++ 的方式保持一致，其背后的价值与前面提到的在自家代码库内保持一致性是相通的。如果 C++ 标准中的某个特性恰好能解决了一个问题，或者某些惯用手段已经广为人知并被接受，这就是使用它的理由。然而，有时标准特性和惯用手段本身存在缺陷，或者在设计时并未考虑到我们代码库的需求。在这些情况下（如下文各节所详述），约束或禁止标准特性的使用是完全合理的。在一些情况下，相较于 C++ 标准库中定义的库，我们更倾向于使用自研或第三方库。这要么是出于对自研或第三方库优越性的认知，要么是因为没有足够的价值将代码库迁移到标准接口。

### 避免反直觉或危险的语言结构 <br> Avoid surprising or dangerous constructs

C++ 包含一些乍看之下合情合理，但实际上远比人们想象中更反直觉或更危险的特性。指南中的某些限制性规则就是为了防止开发者落入这些陷阱。针对此类限制，指南破例豁免的门槛很高，因为一旦豁免此类规则通常会直接带来危及程序正确性的重大风险。

### 避免采用普通 C++ 程序员难以驾驭或维护的语言结构 <br> Avoid constructs that our average C++ programmer would find tricky or hard to maintain

C++ 的某些特性会给代码引入过高的复杂度，因此在通常情况下并不推荐普遍使用。在反复使用的代码（也就是那些被极为广泛复用的底层/核心代码）中，采用相对晦涩复杂的语言结构往往是更加容易被接受的，因为复杂实现所带来的任何收益都会因其庞大的调用量而被成倍放大，而且在开发代码库的新模块时，不需要再次付出理解这种复杂性的认知代价（因为只需使用封装好的接口）。如果不确定能否使用某些复杂特性，可以向项目负责人申请对此类规则的豁免。这一点对我们的代码库尤为重要，因为代码所有权和团队成员会随时间而变化：即使目前维护某段代码的每个人都理解它，也不能保证几年后依然能够理解。

### 时刻警惕我们的规模 <br> Be mindful of our scale

面对拥有上亿行代码和数千名工程师的代码库，一个工程师犯下的一些错误或简化做法（为了省事）可能会让许多人付出高昂的代价。例如，避免污染全局命名空间尤为重要：如果每个人都把东西放进全局命名空间，那么在数亿行代码的代码库中，命名冲突将极难处理并且极难避免。

### 必要时为性能优化让步 <br> Concede to optimization when necessary

性能优化有时是不可或缺且正当合理的，即便某些优化手段会与本文档中提到的其他原则发生冲突。

本文档的宗旨，是在施加合理约束的前提下，提供尽可能最大程度的指导建议。一如既往，常识与良好的编程品味应当始终占据主导地位。在此我们特别说明，所谓的“常识与品味”特指整个 Google C++ 社区业已形成的既定规范与共识，而不仅仅是你个人或你所在团队的偏好。请保持怀疑并尽量克制使用那些自作聪明（奇技淫巧）或不同寻常的语言结构：没有明文禁止，绝不等于获得了准许。运用你的判断力，请毫不犹豫地向你的项目负责人咨询以获取更多的指导建议。
